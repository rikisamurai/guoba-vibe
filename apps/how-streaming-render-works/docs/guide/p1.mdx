# P1：调度器、稳定前缀与尾部修补

第 3 章结尾留下了 P0 的三个症状：尾部裸奔、闪变、O(n²)。P1 用四个部件逐一处理，全部装进一个与 P0 同签名的组件——渲染器下拉里切一下就能对比。

注意三处差异：P1 一侧的文字以平滑的节奏出现（而不是跟着网络抖动一顿一顿）；尾部的 `**` 和 `` ` `` 几乎不裸奔（被乐观补全）；已完成的段落纹丝不动。

## 部件一：显示调度器

P0 的合并提交解决了"提交太频繁"，但显示节奏仍然是网络节奏的采样——burst 到达时一次提交涌出几百字，弱网时半天不动。P1 引入真正的**两只时钟**：

```ts
const scheduler = createDisplayScheduler({
  onEmit: setVisible, // display clock：由调度器决定
  onDrained: () => setDrained(true),
})
scheduler.push(delta) // producer clock：网络说了算
```

内部是一个 visible/pending 双缓冲 + 定时器。两个关键设计：

**自适应速率**。每 33ms 放出的字符数正比于积压量（`pending.length / 6`，夹在 2~240 之间）：弱网时逐字细腻，burst 后快速追平，不会越拉越远。

**grapheme 安全**。放出的单位是 `Intl.Segmenter` 切出的 grapheme cluster，不是码点——`👨‍👩‍👧‍👦` 是 7 个码点 11 个 UTF-16 单元，但永远作为一个整体放出。按码点切会让用户看到半个家庭。

流结束不等于显示结束：producer 完成后进入 **draining**（排空缓冲），排空才算 final。这就是 `StreamStatus` 里 `draining` 状态的来历。

## 部件二：块级切分

要"只重解析变化的部分"，先要能把文本切成块。P1 用一个 60 行的行扫描器（`parse/blocks.ts`）：空行分隔普通块；code fence 开启后进入围栏状态，直到看到同款闭合围栏——没等到就整块标记 `closed: false`。

教学版的诚实声明：setext 标题（下一行的 `===` 会把上一段变成标题）和跨块的链接定义**没有处理**。它们正是"跨块语义迫使多块一起失效"的经典例子，生产级实现（Streamdown 等）为此付出了可观的复杂度。

切分器有一条被单测钉死的关键性质：**append 增量只影响尾块，前缀块逐字不变**——这是稳定前缀缓存能成立的前提。

## 部件三：稳定前缀缓存

有了块，缓存就水到渠成：

```ts
const dirty = i === blocks.length - 1 && !final
if (!dirty && cache.texts[i] === block.text) return cache.htmls[i] // 命中
```

除 dirty 尾块外，每个块的 HTML 按块文本缓存。配合 `React.memo`，html 字符串不变的块连 React 协调都短路——**稳定块的 DOM 完全不被触碰**。这一刀砍掉的不只是 parse 成本：文本选区不再被摧毁、`<video>` 不再重载、CLS 大幅下降。

每次提交的工作量从 O(全文) 降到 O(尾块)。退化点也随之明确：**一段超长且从不换段的输出会让尾块无限膨胀**，P1 退回 P0 的性能——这不是 bug，是这套设计的边界。

## 部件四：尾部修补

dirty 尾块渲染前做一次乐观补全（`parse/remend.ts`）：反引号计数为奇补 `` ` ``，`**` 不平衡补 `**`，剩余单 `*` 不平衡补 `*`；未闭合围栏由块级切分识别后补一行闭合围栏。

两条铁律：

1. **补全结果只进渲染管线**。`rawText` 永远是模型原文——复制、持久化、重发给模型，读的都是原文。
2. **final parse 不修补**。流结束排空后，用原始全文做最后一次渲染。样本结尾那个永不闭合的 `**`，在流式期间被乐观地渲染成粗体，final 后回归字面量——这是"永不回改"三角里被牺牲的那个角，但只牺牲在尾块、只在收口那一刻。

## P1 的账单

得到：平滑的显示节奏、grapheme 安全、稳定块零重渲染、尾部不裸奔。付出：一个调度器的延迟（visible 落后 raw 一点点，这正是文档说的 raw-to-visible latency，评测时必须同报）、块级切分的边界取舍、以及"final 时刻可能回改尾块"这一次性妥协。
