# 开篇：流式渲染为什么难

打开任何一个 AI 聊天应用，回答都是一个字一个字"流"出来的，而且流出来的不是纯文本——标题、表格、代码块边流边成形。这个看起来理所当然的效果，做对了远比想象中难。

如果你多播几次、换几种策略，可能已经注意到一些现象：粗体标记 `**` 有时会短暂地以原始字符露出来，然后"啪"地变成粗体；表格在到齐之前是一堆竖线。这些不是 bug，是**流式渲染的本质困境**的表面症状。

## 不可能三角

流式 Markdown 渲染有一个定理式的约束——以下三者不可兼得：

- **零延迟**：字符一到就显示
- **完全正确**：任何时刻画面都是合法的 Markdown 渲染结果
- **永不回改**：已经显示的内容不再变化

原因在于 Markdown 存在**前视歧义**：`*` 到达时，你不知道它是乘号、斜体的开头还是粗体的一半；`|` 到达时，你不知道后面会不会跟一个表格分隔行。后续字符可以改变前文的含义，所以要么等（牺牲延迟），要么猜（牺牲正确或稳定）。

工程上的答案不是消灭这个三角，而是**选择在哪里妥协、把妥协控制在多小的范围内**。

## 四层问题模型

把"流式 Markdown 很难"拆开，难点分布在四个独立的层：

| 层             | 问题                | 典型坑                                                                    |
| -------------- | ------------------- | ------------------------------------------------------------------------- |
| **传输层**     | 字节怎么到达        | chunk 在 UTF-8 多字节字符中间截断；代理把多个事件缓冲成一坨；断流与取消   |
| **显示调度层** | 到达节奏 ≠ 显示节奏 | 每个网络 chunk 触发一次 React 提交；burst 到达时 UI 卡死                  |
| **语法层**     | 未闭合结构怎么办    | 未闭合的 `**`、代码围栏、表格；前视歧义                                   |
| **渲染层**     | DOM 怎么更新        | 每 token 全文 reparse + innerHTML 全量替换；重型节点（高亮/图表）反复重建 |

其中显示调度层有一个核心心智模型——**两只时钟**：producer clock（网络到达的节奏，抖动、突发、不可控）和 display clock（用户看到的节奏，应该平滑、可控）。二者必须用 buffer + 调度器解耦，任何把它们直接焊在一起的实现都会在真实网络下抖动。

## 方案谱系

按"增量发生在哪一层"，现有方案排成一条谱系：

| 路线                | 思路                         | 代表                         | 适用              |
| ------------------- | ---------------------------- | ---------------------------- | ----------------- |
| 全文重解析          | 每次提交把全文重新 parse     | react-markdown / markdown-it | 短消息、低频更新  |
| 尾部修补 + 全文解析 | 渲染前给未闭合结构补假闭合   | remend 式补全器              | 中等长度          |
| 块级切分 + 稳定前缀 | 冻结已完成的块，只重解析尾块 | Streamdown / Markstream      | AI 聊天主流甜点位 |
| 增量 token/AST      | parser 级增量                | streaming-markdown / Lezer   | 超长文、编辑器    |
| 结构化事件          | 上游直接发结构化 blocks      | AI SDK UI parts              | 工具卡片、富交互  |

越往下延迟与性能越好，复杂度也越高。**不要过度设计**：短消息场景用全文重解析加一个 32~80ms 的合并提交就完全够用。

## 本教程的路线

这套教程配套一个可以动手玩的实验场（`stream-render-lab`），代码全部手写、不依赖任何 AI SDK。我们沿谱系逐级实现，每一级都保留，可随时切换对比：

1. **传输层**（第 2 章）：手写 SSE 解析器，处理所有字节级边界
2. **P0 基线**（第 3 章）：buffer + 合并提交 + 全文重解析 + final parse
3. **回放模拟器**（第 4 章）：可复现的恶意 chunk 时间线，不烧 token 的调试武器
4. **P1 进阶**（第 5 章，撰写中）：显示调度器 + 块级切分 + 稳定前缀 + 尾部修补
5. **P2 重型节点**（第 6 章，撰写中）：Shiki 增量高亮、Mermaid 的两种流式策略

> 本教程的概念框架参考了《AI 对话中的流式 Markdown：方案全景与选型指南（2026）》的四层模型与方案谱系，实现全部为本仓库原创手写代码。
