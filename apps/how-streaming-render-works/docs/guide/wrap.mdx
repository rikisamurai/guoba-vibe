# 收尾：安全基线与评测方法

六章走完，一个从 SSE 字节到 Shiki/Mermaid 的完整流式渲染管线已经立起来了。收尾章做两件事：把散落各章的安全决策集中成清单，把「怎么知道自己做对了」变成方法。

## 安全基线清单

模型输出是**不可信输入**——这是所有决策的出发点。本项目落地的每一条：

| 威胁                              | 防线                                            | 落点                       |
| --------------------------------- | ----------------------------------------------- | -------------------------- |
| 原样 HTML 注入（`<img onerror>`） | `html: false`，一律转义                         | `render/markdown.ts`       |
| `javascript:` / `data:` 链接      | markdown-it `validateLink`，链接语法整体不成立  | 同上（有单测钉死）         |
| Mermaid 图表内 click 绑定/外链    | `securityLevel: 'strict'`                       | `render/mermaid-block.tsx` |
| API key 泄漏                      | key 只存在服务端 `.env`，浏览器只见 `/api/chat` | `server/index.ts`          |
| 用户停止后上游继续烧 token        | 请求 signal 全链路透传                          | 同上                       |
| 渲染修补污染原文                  | 假闭合只进渲染管线，`rawText` append-only       | P1/P2 渲染器               |

一条本项目没踩到但值得记住的边界：sanitize 链管不到业务组件内部的 `dangerouslySetInnerHTML`——如果你在 markdown 渲染之外又给自定义组件开了 HTML 后门，安全审计要单独覆盖它。

## 评测：让同一份输入说话

「感觉流畅多了」不是工程结论。本项目的评测方法论浓缩成三条：

**一、可复现的输入。** 种子化的回放时间线（第 4 章）保证任何对比都在同一份输入上进行。`sliceJitter(transcript, { seed: 42 })` 在任何机器上产出逐字节相同的流。

**二、往返不变量兜底正确性。** 恶意切分 × 三种线级画像，重组必须无损还原原文——这条测试挂了，其他一切指标都没有意义。

**三、分层指标。** 实验控制台里的四个数字各自回答一个问题：

| 指标       | 回答的问题           | 典型值（真实 DeepSeek 长回复） |
| ---------- | -------------------- | ------------------------------ |
| 网络 chunk | 传输层实际压力       | 515                            |
| SSE 事件   | 协议层解析量         | 1954                           |
| UI 提交    | 显示调度层的合并效果 | 202（约 10:1）                 |
| 耗时       | 端到端体验           | 14.8s                          |

评测时的反作弊常识（对自己诚实）：把文本长期扣在 buffer 里换来的「低 CPU」必须同报 raw-to-visible 延迟；用 fade 动画掩盖低提交频率的必须报真实 commit 频率。P1 的调度器引入了 visible 落后 raw 的延迟——这是被记账的妥协，不是被隐藏的魔法。

## 没有做的事（P3 backlog）

诚实的边界清单，也是下一步的路线图：

- **KaTeX 公式通道**：第三类重型节点，渲染后高度突变的 CLS 处理是新功课
- **超长会话虚拟化**：几百条消息的 DOM 总量控制
- **typed SSE / JSON blocks**：工具卡片等结构化内容不该挤在 markdown 文本里
- **遥测**：parse/commit 耗时、Long Task、CLS 进真实监控
- **setext 标题与跨块链接定义**：块级切分的已知语义缺口

## 选型回顾

最后回到第 1 章的谱系表。走完全程之后，选型建议可以说得更硬气了：

- **短消息、低频更新**：P0 一档（全文重解析 + 合并提交）就够，别过度设计
- **典型 AI 聊天**：P1 一档（块级 + 稳定前缀）是甜点位，生产环境直接用 Streamdown（React）/ Markstream（Vue）而不是自己写——但现在你知道它们内部在做什么、坑在哪里
- **重内容（代码/图表/公式）**：确认所选库有 P2 式的重型节点独立调度，没有就得自己补
- **工具卡片、可交互内容**：跳出 markdown，上结构化事件

这套 lab 的价值不在于替代任何库，而在于：下次某个流式渲染库出了怪 bug，你能在五分钟内说出它大概率坏在四层模型的哪一层。
