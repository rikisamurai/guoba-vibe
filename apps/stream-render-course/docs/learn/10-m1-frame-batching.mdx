## 先看失败：`rAF` 不会自动帮你去重

假设 12 ms 内连续到达 `你` `好` `，` `🙂` `！`，60 Hz 屏幕下一帧约在 16 ms。直观写法会排队五个 callback：

```ts
function onDelta(delta: string) {
  raw += delta
  requestAnimationFrame(() => publish(raw))
}
```

arrival 发生了五次，用户在第一帧只能看到最后一个结果，但 React 仍可能做五次无法被看见的工作。

```text
arrival:  0ms  3ms  6ms  9ms  12ms
raw:      你   你好   你好，  你好，🙂  你好，🙂！
display:                    16ms → 你好，🙂！
```

M1 不改 Markdown，只让一个 pending frame 拥有下次发布权。

## 原理：两只时钟，一个所有者

```text
arrival clock: delta 到达 → raw 立即追加 → pending 合并
display clock: frame boundary → flush 一次 → visible 向 raw 追赶
```

`cancelFrame !== null` 表示“已经有一个 task 负责下次 flush”。后来的 delta 只进 `pending`，不再注册 frame。

```ts
interface FrameBatcherState {
  pending: string
  cancelFrame: (() => void) | null
}
```

Clock 是依赖而不是全局变量，所以 contract 能精确 `advanceFrame()`，不需要 sleep 或猜 CI 速度。

## TODO：实现 frame ownership

打开 `exercise/frame-batcher.ts`，完成唯一 TODO。你需要三个动作：

```ts
push(delta) // 追加 pending；只在无 owner 时申请 frame
drain() // 取消 pending frame，同步 flush 已接受内容
cancel() // 取消 frame，丢弃尚未发布的 pending
```

`flush` 要先放弃 owner，再取走 pending；否则 commit 期间到达的新 delta 无法预约下一帧。

```ts
function flush() {
  cancelFrame = null
  const batch = pending
  pending = ''
  if (batch !== '') commit(batch)
}
```

## 为什么 terminal 不能只是取消 frame

如果 `[DONE]` 在 13 ms 到达时直接 cancel，`raw` 已是完整答案，`visible` 却可能仍为空。所以协议终态走 `drain`；用户主动停止才走 `cancel`。

```text
terminal proof → drain pending → visible === raw → settled
user cancel    → drop pending  → no late commit
```

## Solution diff

```diff
-push(delta) { commit(delta) }
+push(delta) {
+  pending += delta
+  cancelFrame ??= clock.frame(flush)
+}
+drain() { cancelFrame?.(); flush() }
+cancel() { cancelFrame?.(); cancelFrame = null; pending = '' }
```

## Checkpoint

- [ ] burst 入口时 raw 已完整，frame 前 commit 仍为 0。
- [ ] 同帧只有 1 个 pending task，推进后只 commit 1 次。
- [ ] drain 不丢尾部也不重复 commit；cancel 后无 late update。

## Invariant / Trade-off / 退化条件

- **Invariant：**每个 frame boundary 最多一次 preview commit；settled 前 `visible === raw`。
- **Trade-off：**用最多一帧的可见延迟，换掉同帧内无法被看见的重复工作。
- **退化：**delta 慢于帧率时收益很小；单次 parse 已超 frame budget 时，M1 也无法消除长任务。
- **环境边界：**后台页签可暂停 rAF，因此终态必须有明确 drain 策略。

## 常见错误

| 现象              | 原因                     | 修复                            |
| ----------------- | ------------------------ | ------------------------------- |
| 同帧仍多次 commit | 每个 delta 都注册 frame  | 用 `cancelFrame ??=` 表达 owner |
| drain 后重复一次  | 没取消原 frame           | 先 cancel handle 再 flush       |
| cancel 后还更新   | handle 或 pending 未清空 | 取消 task 并清空所有权          |
