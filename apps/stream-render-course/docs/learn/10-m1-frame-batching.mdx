# 同一帧来了三次正文，需要更新三次吗？

**修改文件：** `apps/stream-render-lab/src/my-chat/publish.ts`。先通过 A、B 的正确性验收；现在优化同一个项目的发布次数。

## 第一步：先运行失败的时序

```bash
pnpm --filter stream-render-lab practice test batch
```

初始实现每次 push 直接 show。验收会在同一帧依次传入“你”“你好”“你好！”，预期只发布最后的“你好！”。

注意这里 push 接受**完整的当前正文快照**，不是文本 delta。应该替换 pending 为最新值，不能把三个快照拼成“你你好你好！”。

## 第二步：只保留一个待执行帧

沿用文件中的 FrameClock 接口：

1. push 保存最新快照。
2. 仅在没有待执行任务时调用 clock.request。
3. 帧回调清除任务标记，取出最新快照并发布。
4. 下一批输入再申请新的帧。

只把 show 包进 requestAnimationFrame 不会自动去重；三个调用仍可能产生三个回调。注入的时钟让测试可以精确决定何时进入下一帧。

## 第三步：修复结束和取消

- finish：取消已排队的帧，立即发布尚未显示的最后快照；下个 tick 不能再发布一遍。
- cancel：取消帧并丢弃待发布快照，后续 tick 不得更新界面。
- 用户停止：上层可先 finish 保留已接受内容，再 cancel 清理；这两个操作不是同义词。

逐项修改 `publish.ts`，再跑：

```bash
pnpm --filter stream-render-lab practice test batch
pnpm --filter stream-render-lab practice test
```

预期 batch 三类时序通过；A、B 已完成时，全量自己的验收也应通过。

## 第五步：测量合帧的收益和等待

在 `src/my-chat/render-policy.ts` 将 profile 设为 M1；在 <LabLink path="/profiler">性能实验</LabLink> 选择基线 M0、对照“我的实现”。这里测的是配置选中的共享引擎策略，不是直接测 publish.ts 的函数耗时。

保持同一语料，先用短到达间隔，再改为慢速输入。分别观察发布、React commit、正文等待显示的延迟。预期突发输入更可能合并；当每段已跨越不同帧时，不能期待同样的次数收益。

**验收：** 正文相同、尾段不丢、取消无迟到更新；报告更新减少的同时说明等待代价。帧调度还受刷新率与后台页面节流影响，不能把 16 ms 当成固定承诺。
