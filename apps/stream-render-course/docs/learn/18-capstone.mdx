# 项目已经在你手里，现在证明它可靠

前面的改动都保留在 `apps/stream-render-lab/src/my-chat/`。本课不创建第三份项目，也不要求你复制参考目录：**你一直运行的“我的实现”就是本次交付。**

## Step 1：确认验收对象

打开 <LabLink path="/project?source=mine">我的 Mini Chat</LabLink>，确认当前源码选择是“我的实现”。在编辑器中打开下面这些文件：

| 阶段               | 你的实现                       |
| ------------------ | ------------------------------ |
| 字节还原           | `src/my-chat/decode.ts`        |
| SSE 事件           | `src/my-chat/parse-events.ts`  |
| 正文与协议结束     | `src/my-chat/read-event.ts`    |
| 响应读取与生命周期 | `src/my-chat/read-answer.ts`   |
| 发布时机           | `src/my-chat/publish.ts`       |
| 渲染集成           | `src/my-chat/render-policy.ts` |

服务端固定响应、页面与安全渲染器是共享外壳。你完成的是这些边界的实现与集成，不是独立重写整个 Lab。

## Step 2：分别验收已完成的模块

```bash
pnpm --filter stream-render-lab practice test utf8
pnpm --filter stream-render-lab practice test sse
pnpm --filter stream-render-lab practice test provider
```

预期 A、B 主线这四组通过。若失败，从对应源文件与反例修复，再回到页面复测。C1 的 batch 优化尚未完成时，全量 practice 仍可能失败；这不是让你忽略失败，而是明确下一阶段还欠哪项能力。

```bash
pnpm --filter stream-render-lab practice test --reference
```

参考验收应全部通过，用于确认课程基线。如果你的验收失败、参考通过，继续修自己的代码；切换页面来源不会改写它。

## Step 3：同一响应，改变交付方式

在 Mini Chat 中运行当前实现验收，固定逐字节输入与虚拟帧时钟会稳定检查边界。

再到 <LabLink path="/playground?demo=network-inspector&source=mine">我的网络观察器</LabLink> 比较分段、刻意拆分、缓冲等真实 HTTP 场景。reader.read 的次数可以变化，完整响应的正文与协议判断仍应一致。两种证据互相补充，不能把固定验收的切点当成生产网络规律。

## Step 4：逐项验收浏览器行为

| 操作           | 预期                                   |
| -------------- | -------------------------------------- |
| 分段发送       | 第一段提前出现，正文逐步增长，最后完成 |
| 缓冲发送       | 首次出现更晚，最终内容一致             |
| 中途断开       | 已收部分保留，明确标记截断             |
| HTTP 503       | 错误归属本轮，之后可重新发送           |
| 接收中停止     | 已收部分保留，之后不再追加             |
| 停止后立即重发 | 新轮独立增长，旧回调不能覆盖           |
| 重试上一条     | 新增一次尝试，不拼到旧半截后           |
| 键盘与窄屏     | 输入、发送、停止、历史均可访问         |

记录失败对应的层：服务端、读取、解码、事件、正文、发布或渲染。不要把所有问题都记成“流式异常”。

## Step 5：保留工程回归结果

```bash
pnpm --filter stream-render-lab test
pnpm --filter stream-render-lab build
pnpm --filter stream-render-course verify
pnpm --filter stream-render-course test:e2e
```

工程回归验证共享实现和页面；`practice test` 才是你自己的边界验收。命令不是互相替代的。页面效果改变后同时检查本地 UI，不能只看测试退出码。

## Step 6：走向优化或真实模型

先在当前项目完成 C 段：实现合帧，配置并对比渲染策略，输出有固定条件的性能报告。不要换一个项目重新开始。

若要验证真实服务，按 Lab README 的 Live 部分配置服务端密钥，再用 <LabLink path="/chat">真实模型聊天</LabLink>。那是现有完整引擎的可选演示；它运行成功不替代你的 practice 验收。将自己的链路接入业务时，要按实际服务商协议、错误和权限重新验收。

**交付标准：** A、B 验收通过；能从点击发送一路定位到屏幕，说明任一故障该在哪层修复。此时已有可靠基线，下一步再追求更少工作。
