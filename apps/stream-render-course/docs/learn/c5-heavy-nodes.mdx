# 旧图表最后完成，为什么覆盖了新内容？

高亮、公式和图表是异步的慢任务，发起顺序和完成顺序没有关系。流式时同一个代码块会被反复提交，早发起的任务完全可能最后才返回。防住它的办法是给每个任务一个版本号，结果回来时先核对“我还是最新的吗”，不是就丢弃。少启动任务（防抖）省的是成本，提交前核对版本保的是正确，两件事不能互相代替。

**修改文件：** `src/my-chat/task-gate.ts`。**集成入口：** `src/my-chat/render-policy.ts`。**共享实现：** `src/heavy/task-gate.ts`、`coordinator.ts`。路径相对 `apps/stream-render-lab/`。

## 第一步：先让昂贵工作暴露出来

在 <LabLink path="/lab">渲染实验台</LabLink> 输入代码围栏、公式或 Mermaid，用 M3 回放，记录基础显示；再用 M4 观察增强任务启动与最终结果。M3 不启用这些重型增强，因此这里比较的是新增能力的成本与调度，不是用零任务作为错误的慢基线。

## 第二步：将项目切到 M4 对照

把 `myRenderPolicy.profile` 改成 M4，在 <LabLink path="/profiler">性能实验</LabLink> 选基线 M3、对照“我的实现”，语料用“代码与公式”。记录新增增强任务数、耗时与最终效果，同时检查正文语义和终态。M4 做了 M3 没有做的工作；不能因任务数更多就说更差，也不能将这组对比写成“重型任务减少”。

这是比较共享策略的集成效果，不声称重新实现了高亮或 Mermaid 算法。

## 第三步：自己拦住迟到的结果

```bash
pnpm --filter stream-render-lab practice test gate
```

起点的 `createTaskGate` 谁先完成就提交谁。验收按“发起 A、发起 B、B 完成、A 完成”的顺序运行，预期只提交 B。修三件事：

1. 每次 push 递增一个版本号；任务完成时，只有版本仍是最新才 commit。
2. dispose 之后，任何结果都不再提交。
3. 与上一次相同的输入不重复启动任务。

这个练习不含防抖和超时，由验收单独运行；这两项在下一步的共享实现里看。

## 第四步：用乱序完成验证任务门禁

打开 task-gate.test.ts 的 never commits a stale async result。标出发起旧任务 A、发起新任务 B、B 完成、A 完成的顺序。

在 `task-gate.ts` 找到任务键和 revision 检查。只防抖启动次数不够：已经启动的旧任务仍可能最后返回；提交前必须确认版本仍然有效。

## 第五步：补一个停止或乱序反例

添加一个任务在 dispose 后返回的用例，或使用不同完成顺序验证只允许当前版本提交。不要删掉版本判断让测试迎合错误实现。

```bash
pnpm --filter stream-render-lab exec vitest run src/heavy/task-gate.test.ts src/heavy/incremental-highlighter.test.ts
pnpm --filter stream-render-lab practice test
```

预期：旧结果不倒灌，停止后不写回，自己的基础链路仍通过。

## 第六步：确认失败不会永远阻塞完成

阅读 deadline 与错误路径。图表失败或超时应有可解释的诊断，不能让整条回答永久停在等待。

把三件事分开：合帧减少状态发布；debounce 减少昂贵任务启动；版本检查拒绝过期结果。它们的收益与正确性职责各不相同。
