```ts
const fixture = {
  chunks: ['边', '到达', '，边', '显示。'],
```

第 N 个片段在 `intervalMs * (N + 1)` 时到达，时间从 replay 开始计算，不是 wall-clock 时间。

后续真实 source 会把相同交付语义暴露为 `AsyncIterable`；本课先用 callback 看清 Clock ordering，不同时学习两种抽象。

## 最小原理：Clock 是依赖，不是全局环境

```ts
interface Clock {
  now(): number
  after(ms: number, task: () => void): void
}
```

生产环境可以用 timer 实现；测试传入 `VirtualClock`。业务代码只依赖上面两个动作，所以测试无需 sleep，也不与机器负载竞争。

```text
clock = 7ms   nothing
clock = 8ms   deliver "边"
clock = 16ms  deliver "到达"
clock = 32ms  deliver "显示。" and settle
```

## 内嵌实验：只有 Clock 前进，字符串才前进

先单步推进，再一次跑完；对照 elapsed time 与已交付片段。重置后相同步骤必须得到相同 timeline。

## Solution diff

```diff
-export function replayText(_input: ReplayInput): Promise<void> {
-  return Promise.resolve()
+export function replayText(input: ReplayInput): Promise<void> {
+  return new Promise((resolve) => {
+    input.chunks.forEach((chunk, index) => {
+      input.clock.after(input.intervalMs * (index + 1), () => {
+        input.onDelta(chunk)
+        if (index === input.chunks.length - 1) resolve()
+      })
+    })
+  })
 }
```

## Checkpoint：时间边界可证明吗

- [ ] `advanceBy(7)` 不会提前交付第一段。
- [ ] 再前进 1 ms 后只出现 `边`。
- [ ] 前进到 32 ms 后，拼接结果精确为 `边到达，边显示。`。

**Invariant：** 任何时刻 `t`，只交付 deadline 不晚于 `t` 的片段，并保持 chunks 顺序。

**Trade-off：** 注入 Clock 增加一个 interface，却换来零 sleep、零 flaky 的 timeline 测试。

**退化条件：** 同一毫秒有大量片段时会连续触发大量 callback；这一课如实保留，后面再合并显示工作。

## 常见错误

- 把第 N 段安排在 `intervalMs * N`，导致第一段 0 ms 提前出现。
- 在测试里同时使用 fake timer 和 `VirtualClock`，产生两套时间源。
- 为了“方便”调用 `Date.now()`，让 replay 无法完全控制。
