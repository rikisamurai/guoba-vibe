这一课不要求你实现任何优化。你只要确认环境、找到将持续演进的 mini-chat，并能说出一段网络响应从 byte 到 React 的最短路径。

## 先看终点：同一份回答，为什么感受不同

下面两列吃的是**同一条 trace**。M0 每到一小段就立即公开一次；M4 代表课程终点的优化版。现在不用懂它们怎么实现，只看四件事：

- `arrival clock`：小段什么时候真正到达。
- `raw`：程序已经收到的完整原文，不能因为渲染慢就丢字。
- `display clock`：浏览器决定什么时候把新画面交给你。
- `visible`：此刻屏幕上真正看得见的内容。

点击开始后，先看 `raw` 是否同速增长，再看 `visible` 和 commit 数。你应该得到第一个直觉：

```text
网络到达节奏 ≠ 屏幕更新节奏
raw 是事实，visible 是当前发布给用户的版本
```

后面的每一课都只会解开这个对照里的一层，不会让你直接复制一个黑盒。

## 为什么从非流式 Chat 开始

如果直接从一堆网络事件开始，你很难判断错误属于协议、状态还是渲染。我们的路线先建立一个“等完整字符串再显示”的正确版本，再一层层替换输入边界：

```text
bytes → UTF-8 text → SSE event → provider delta → chat state → React
```

这六层不能因为都包含“文本”就合成一个函数。后面的每个线上怪问题，都能落回其中一条边界。

## 找到唯一 TODO

打开 `exercise/run-comparison.ts`。完整问题只有一行：

```ts
export async function runComparison(): Promise<QuickStartComparison> {
  const baseline = await runProfile('M0')
  // TODO 00: 用课程终点 profile 跑右侧，不要把 M0 结果重复比较一次。
  const challenger = await runProfile('M0')
  return { baseline, challenger }
}
```

`baseline` 是从零开始学习时的基线；`challenger` 应该代表课程完成后的 M4。两次运行仍使用相同的 fixture、16 ms frame 和 direct reveal，所以唯一变量只能是 profile。

## Contract 到底证明了什么

不要只看“测试绿了”。这三个断言分别保护三件不同的事：

```text
两次 outcome 都是 completed
→ 两次最终 raw 完整且相同
→ 两次最终 Render IR 等价
→ M4 用更少 commit 到达相同终点
```

如果只断言 commit 更少，丢掉半句话也可能“性能更好”。所以性能结论必须排在正确性之后。
