# 回答一万字，每来一段就重算一万字？

追加一段文字，通常只影响文档的尾巴。如果能找到一个位置，保证它之前的块不会被后来的字符改变，就只需要从那里重新解析；这个位置就是稳定边界。找边界宁可保守：最后一块总是脏的，它前面的列表可能把它吞进去，引用定义则能改变全文任何位置的含义。拿不准就回退全文解析，慢一点，但不会错。

**修改文件：** `src/my-chat/dirty-start.ts`。**集成入口：** `src/my-chat/render-policy.ts`。**算法入口：** `src/markdown/preview.ts` 的 parseM3。路径相对 `apps/stream-render-lab/`。

## 第一步：先记录全文解析的工作量

打开 <LabLink path="/profiler">性能实验</LabLink>，基线选 M2，语料选“大量独立段落”，记录累计解析字符量。不要先猜一个提升百分比。

相同前缀被反复解析会累积额外工作；屏幕只刷新几次，也不代表解析只做了几次。

## 第二步：让自己的项目使用 M3

将 `myRenderPolicy.profile` 改为 M3，保存后在性能页将对照设为“我的实现”。保持语料、规模、分片与节奏相同，重新采样。

预期在存在稳定段落边界的输入上，解析工作量有机会降低。结果必须同时满足原文、最终语义与终态一致。

## 第三步：自己决定从哪一块重算

```bash
pnpm --filter stream-render-lab practice test suffix
```

`dirtyBlockIndex` 收到上一帧的块列表（每块的类型，以及是否含引用定义），返回追加之后要从第几块开始重新解析；返回 null 表示只能全文解析。起点永远返回最后一块，三个独立段落时是对的。按失败项补上三种情况：

1. 只有一块时，没有可以依靠的边界。
2. 最后一块前面是列表时，新来的列表标记可能把尾段并进去，要从列表开始。
3. 任何块里出现引用定义时，它能改变全文的引用，直接回退。

这个练习由验收单独运行，不接入 Mini Chat 的显示。

## 第四步：解释稳定边界

打开 parseM3，找到与你刚写的三条判断对应的分支，再沿 dirtyStart、parsedTail 与 blocks 拼接追踪一次追加。算法保留稳定前缀，从可能变化的尾块重新解析。

不要机械截最后 100 个字符；列表、引用和表格可能跨越那个位置，切在结构内部会改变含义。

## 第五步：主动触发回退

在 <LabLink path="/lab">渲染实验台</LabLink> 比较 M2、M3：先用引用链接，再在末尾追加定义，观察 global_definition_fallback；再用无稳定边界的长段落，查看 no_quiescent_checkpoint。

回退保证正确性。若只展示最有利的短段落，就无法回答它何时不值得使用。

## 第六步：逐追加点与基线比较

在 `src/markdown/markdown.test.ts` 找到 adversarial append checkpoint 用例，新增嵌套列表，验证每个追加点与 M2 基线的语义一致，而不只是最终一致。

```bash
pnpm --filter stream-render-lab exec vitest run src/markdown/markdown.test.ts
pnpm --filter stream-render-lab test:bench
```

验收报告写清：哪类语料减少工作，哪类触发回退，最终是否仍正确。不能由一个有利语料宣称任意 Markdown 都支持严格线性的增量解析。
