# 流还在继续，用户已经开始读了

**项目文件：** `apps/stream-render-lab/src/learn-project/project-page.tsx` 与 `use-mini-chat.ts`。这两个共享外壳调用你在 `src/my-chat/` 完成的链路；本课做交互故障验收。

## 第一步：快速停止并重发

打开 <LabLink path="/project?source=mine">我的 Mini Chat</LabLink>，第一段出现后立即停止，再发送另一条消息。

预期：旧回答保留，新回答独立增长；旧任务不能覆盖新轮的状态。记下每一轮的正文和终态，而不仅仅观察发送按钮能否再次点击。

## 第二步：沿着可疑更新找到源头

在 `use-mini-chat.ts` 的状态发布位置临时记录请求 id。重复第一步，检查迟到回调是否仍能通过当前轮检查，之后移除日志。

如果旧轮仍在追加，先检查共享读取循环 `src/practice/consume-response.ts` 是否在每次读取和每个事件前检查 signal，再看 `use-mini-chat.ts` 的 `current()` 是否拦住旧回调；如果正文已停止但 UI 状态倒退，检查待发布帧和自己 `my-chat/publish.ts` 的 cancel。用产生问题的那一层修复，不加一个新的全局 busy 锁来遮住竞态。

## 第三步：验收历史与重试语义

1. 连续完成两轮，前一轮文本不应重新拼接。
2. 第三轮中途停止，保留前三轮记录。
3. 重试上一条，产生新尝试；旧的半截内容不被伪装成成功。重试使用当前选择的服务场景，想看到成功的新尝试，先切回“分段发送”。
4. 选择 HTTP 错误，确认输入恢复可用，错误信息属于对应轮次。

教学历史保存在内存，刷新即清空；这门课不把持久化列为流式协议的一部分。

## 第四步：检查阅读与可访问性

用键盘提交、停止和重试，再缩窄窗口。状态通过 role=status 表达，正文不应每个增量都强制播报。

当前教学项目不强制自动滚动。若你的业务需要跟随，只在用户接近底部时跟随；用户上翻读历史后停止抢滚动，再提供“回到最新”入口。把它当作明确的阅读策略，不要在每次 text 更新时无条件 scrollIntoView。

## 第五步：把问题保留为回归用例

```bash
pnpm --filter stream-render-lab practice test lifecycle
pnpm --filter stream-render-course test:e2e
```

前者检查自己的读取取消；后者检查浏览器交互。若你修了一个竞态，新增能稳定复现该时序的用例，验证停止后再等一段时间正文也不增长。

预期：普通、停止、重试和失败路径都能继续操作；测试通过之外，还能解释哪一层阻止了旧结果。
