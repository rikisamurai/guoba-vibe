# 半截代码围栏，先显示成什么？

**自己的集成入口：** `apps/stream-render-lab/src/my-chat/render-policy.ts`。共享算法入口：`src/markdown/repair.ts`。本课配置并验证现有预览能力，同时通过添加反例理解实现。

## 第一步：先保留基线现象

在 <LabLink path="/lab">渲染实验台</LabLink> 输入未闭合代码围栏，选择 M1，回放到中途暂停。记录原文与当前显示，不要只截最终完成后的页面。

问题：若临时补一个结束围栏，显示可以更稳定，但那几个字符并不是服务端真的发来的。

## 第二步：为我的项目选择 M2

在 `render-policy.ts` 把 profile 改为 M2，保存后回到 <LabLink path="/project?source=mine">我的 Mini Chat</LabLink> 重新发送，确认仍是自己的实现。

M2 包含预览修补与稳定块复用。相较 M1，差异不只有速度；不要把所有变化都写成“性能提升”。

## 第三步：追踪修补的副本

打开 `src/markdown/repair.ts`，找到修补文本与 syntheticRanges。再看 preview 如何使用它们。

预期：raw 保留真实输入，repair.text 可以有临时补全。完成时以原文的 canonical 解析为准，临时星号或括号不能保存进历史，也不能标成模型真实输出。

## 第四步：加一个会拆穿简单规则的用例

在 `src/markdown/markdown.test.ts` 找到 adds synthetic closers 与 ignores emphasis markers inside inline code spans。新增自己的未闭合片段，验证：

1. 中间态可以修补，原文始终不变。
2. 真正结束符到达后，不会重复补全。
3. 代码中的星号不会被误当作强调标记。

```bash
pnpm --filter stream-render-lab exec vitest run src/markdown/markdown.test.ts
pnpm --filter stream-render-lab practice test
```

## 第五步：比较体验与代价

在 <LabLink path="/profiler">性能实验</LabLink> 比较 M1 与“我的实现”（当前 M2），保持语料、切分与节奏相同。先检查最终语义一致，再看解析工作和渲染指标。

修补是体验策略，不是完整语法证明。不支持的结构应保守显示；让页面看起来稳定，不能以篡改正文为代价。
