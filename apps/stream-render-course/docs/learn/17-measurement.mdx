# 更新少了，就一定更快吗？

**类型：性能实验。** 先完成正常功能，再测性能。本课不要求你先认识火焰图的全部细节。

## 第一步：选一个明确的问题

例如：“按帧合并是否减少状态发布？”或者“尾部解析是否减少累计解析字符量？”一次只回答一个问题。

打开 <LabLink path="/profiler">性能分析</LabLink>，先看页面的指标说明。开发模式可以学习流程，正式比较请使用生产构建。

## 第二步：固定实验条件

保留相同文本、随机种子、切分大小、到达间隔和机器环境，只切换策略。不要把短文本 M0 与长文本 M4 比较，也不要把两台机器的毫秒数直接相减。

## 第三步：先验证内容

两种策略的最终原文、显示正文与终态必须一致。丢掉一半内容当然可能更快，但不构成优化。

## 第四步：分开看三个指标

| 指标                | 说明什么             | 不能单独证明什么           |
| ------------------- | -------------------- | -------------------------- |
| 状态发布次数        | 调度频率             | React 必然同次数提交       |
| 累计解析字符量      | 算法实际处理的输入量 | 某台设备上的毫秒耗时       |
| React Profiler 时间 | 被测组件渲染工作     | 完整网络耗时和屏幕绘制时间 |

首段到达、首次可见与全部完成也要分别记录。Mini Chat 当前显示的首段正文时间不是 paint 时间。

## 第五步：运行确定性工作量测试

```bash
pnpm --filter stream-render-lab test:bench
```

测试用固定语料和虚拟时钟比较规模增长，避免把机器偶发负载当成复杂度结论。长段落没有稳定边界时，M3 允许回退；必须记录原因。

## 第六步：再看浏览器结果

```bash
pnpm --filter stream-render-lab build
pnpm --filter stream-render-lab preview
```

打开终端打印的 preview 地址，再进入 /profiler。不要用仍在运行的 5174 开发页冒充 production。重复采样，记录策略、输入、构建模式、浏览器与异常值。

练习：写一段结论，包含正确性结果、固定条件、改善的指标和没有测量的部分。禁止只写“提升 80%”却不写基线。

预期：测试通过，同输入下最终内容一致；报告中的每项结果都能对应到输入、策略和构建环境。
