# 优化完成以后，拿什么证明？

**本课交付：** 一份能重现的 A/B 报告。自己的渲染配置来自 `apps/stream-render-lab/src/my-chat/render-policy.ts`；性能页也使用这份配置。

## 第一步：先验收自己的正确性

```bash
pnpm --filter stream-render-lab practice test
pnpm --filter stream-render-lab test:bench
```

第一条覆盖你的字节、事件、协议、生命周期与发布实现；第二条验证共享算法的确定性工作量。C1 完成后两者应通过。不能靠丢字、提前完成或不渲染内容来获得更快数据。

## 第二步：声明本次比较的问题

在 <LabLink path="/profiler">性能实验</LabLink> 明确选择基线和对照，支持 M0–M4 与“我的实现”。推荐一次回答一个问题：

| 比较    | 合适的语料与问题                                     |
| ------- | ---------------------------------------------------- |
| M0 → M1 | 混合 Markdown；合帧是否减少更新，增加多少等待？      |
| M1 → M2 | 混合 Markdown；预览、引用复用如何影响成本？          |
| M2 → M3 | 稳定短段落；累计解析工作是否减少，何时回退？         |
| M3 → M4 | 代码与公式；新增增强的成本、启动时机与最终效果如何？ |

“我的实现”解析成当前 policy 的策略，页面与导出报告应能说明它是哪一个。这里不直接测你自己的 HTTP reader 和 publish.ts；它们由实践验收与 Mini Chat 单独验证。

## 第三步：固定其他变量

保持相同语料、文本规模、delta 大小、到达节奏、预热与重复次数。规模以 UTF-16 code units 标注，不能将它写成网络 KB 或模型 token 数。

字节到达节奏是可重复的模拟输入，解析和 React 渲染在当前浏览器真实执行；这不是网络测速。选慢速到达再测一次，观察合帧优势是否改变。

## 第四步：使用生产构建

```bash
pnpm --filter stream-render-lab build
pnpm --filter stream-render-lab preview
```

打开终端打印的 preview 地址，再进入 `/profiler`。不要继续拿 5174 开发页报告生产性能。保持同一浏览器、窗口状态和机器环境，等待预热与全部重复采样完成。

## 第五步：先检查正确性，再读成本

| 指标                                  | 回答什么                         | 不代表什么                   |
| ------------------------------------- | -------------------------------- | ---------------------------- |
| raw / visible / canonical / completed | 两组内容、最终语义和终态是否正确 | 覆盖所有生产输入             |
| 状态发布、React commit                | 调度与渲染分别发生多少次         | 两者必然一一对应             |
| 累计解析字符量                        | 算法重复处理了多少输入           | 某台机器的耗时               |
| React 渲染时间、长任务                | 本次浏览器中的工作与阻塞         | 完整网络、GPU 或 paint 耗时  |
| 首次 visible、raw-to-visible 延迟     | 数据接受到发布的等待             | 字已真正绘制到屏幕的精确时间 |

把改善与代价放在一起：例如减少解析工作，但短回答没有明显时间收益；或减少发布次数，同时增加等待。样本波动过大时先解释环境，不挑最好的一次。

## 第六步：导出并写结论

使用页面的导出报告，保留配置与每次样本。结论至少包含：

```text
问题：本次只比较什么？
条件：构建、浏览器、语料、规模、切分、到达节奏、重复次数。
正确性：原文、最终语义和终态是否一致？
结果：哪个指标改善，哪个指标没有改善或变差？
边界：回退、波动、未测量部分，以及不适用的输入。
```

预期他人使用同一输入与策略能重复实验过程；不要求每台机器得到完全相同的毫秒值。

**完成课程：** 你有能通过自己的验收的 Mini Chat，也有一份清楚区分真实网络、确定性 fixture 和浏览器测量的优化结论。
