# SSE 不是 `split("\n\n")`

浏览器 Network 面板里的一块响应数据，可能只包含半个 emoji，也可能一次包含三个 SSE event。只要 parser 把 transport chunk 当成字符或事件边界，线上偶发的中文乱码、JSON parse error 和“回答突然截断”就会同时出现。

## 本章完成标准

你不是要背一遍 SSE 字段，而是要实现并证明下面这条性质：

```text
parse(partition(bytes, 任意切法)) === parse([bytes])
```

完成后，你应该能够：

- 解释 transport chunk、UTF-8 code point、line 和 SSE event 四种边界为何互不相同。
- 正确处理 BOM、CR、LF、CRLF、多行 `data`、comment、`id`、`retry` 和未知字段。
- 说明为什么 EOF 前没有空行的残留 data 必须丢弃。
- 从 Network 中的一串 bytes 追到 provider adapter 收到的 event。

## 先制造一个线上才容易出现的失败

很多 SSE 教程从这段代码开始：

```ts
for await (const chunk of response.body) {
  const text = new TextDecoder().decode(chunk)
  for (const event of text.split('\n\n')) {
    consume(JSON.parse(event.replace('data: ', '')))
  }
}
```

它同时做错了三件事。

### 错误一：每个 chunk 新建 decoder

字符 `你` 的 UTF-8 是三个 byte，emoji `🙂` 是四个。网络可以在任何 byte 后切开：

```text
你  = E4 BD A0
🙂 = F0 9F 99 82

chunk A: E4 BD
chunk B: A0 F0 9F
chunk C: 99 82
```

每块单独 decode 会产生 replacement character `�`。正确做法是复用一个 decoder，并在中间调用 `decode(chunk, { stream: true })`。

### 错误二：只认识 LF 双换行

SSE 规范允许三种行结束：LF、CR、CRLF。更棘手的是 CRLF 自己也能跨 chunk：

```text
chunk A: "data: first\r"
chunk B: "\ndata: second\r\n\r"
chunk C: "\n"
```

`split("\n\n")` 既看不到独立 CR，也可能把跨块的 CRLF 拆错。

### 错误三：一行不等于一个事件

下面是**一个** message event：

```text
: heartbeat
event: answer
id: 42
data: 第一行
data: 第二行

```

它的 data 是 `第一行\n第二行`。comment 不产生事件，未知字段被忽略，空行才触发 dispatch。

## 正确分层：四个状态机，不是一团字符串

```text
Uint8Array chunks
  │  TextDecoder(stream=true)
  ▼
Unicode text fragments
  │  CR / LF / CRLF line scanner
  ▼
complete lines
  │  field parser + event buffer
  ▼
SSE message / retry control
  │  provider-specific JSON adapter
  ▼
typed SourceEvent
```

每一层只做一件事，也只暴露一类错误。

### Layer 1：增量 UTF-8

一个 decoder 必须活完整条连接：

```ts
const decoder = new TextDecoder('utf-8')
let text = ''

for await (const chunk of chunks) {
  text += decoder.decode(chunk, { stream: true })
  // 只交出完整行，残留保留到下一块
}

text += decoder.decode()
```

默认 TextDecoder 会处理流开头的 UTF-8 BOM；不要对每个 chunk 手动删除 `\uFEFF`，否则中途真实出现的同字符也会被误删。

### Layer 2：增量行扫描

scanner 返回 `{ lines, rest }`。遇到末尾孤立 `\r` 时不能立即认定一行结束，因为下一块可能以 `\n` 开头。

| 当前字符  | 下一字符 | 行结束长度 | 动作                 |
| --------- | -------- | ---------- | -------------------- |
| `\n`      | 任意     | 1          | 产出前面的 line      |
| `\r`      | `\n`     | 2          | 产出一行，跳过两字符 |
| `\r`      | 其他     | 1          | 产出一行             |
| 末尾 `\r` | 尚未 EOF | 未知       | 留在 rest            |

### Layer 3：字段与 buffer

字段语法是“第一个冒号前为 name，冒号后可去掉**一个**前导空格”：

```text
data:test       → name=data, value=test
data: test      → name=data, value=test
data:  test     → name=data, value=" test"
data            → name=data, value=""
```

状态至少包括：

```ts
interface EventState {
  data: string[]
  eventType: string
  lastEventId: string
  hasLastEventId: boolean
}
```

- `data`：逐行追加，dispatch 时用 `\n` 连接。
- `event`：只影响当前 buffered event，dispatch 后清空。
- `id`：不能包含 NULL；有效值跨 event 持续存在，空值表示重置。
- `retry`：只有全部为 ASCII 数字才有效，它更新重连等待，不必等 data dispatch。
- `:` 开头：comment，通常承载 heartbeat，不进入 data。

### Layer 4：空行 dispatch

空行不是 data，它是提交边界：

```ts
if (line === '') return dispatch(state)
```

如果没有 buffered data，空行不产生 message。dispatch 后清空 data 与 event type，但保留 last event ID。

## EOF 为什么不是隐式空行

考虑连接突然断在这里：

```text
data: {"partial": true
```

如果 parser 在 EOF 自动 dispatch，上层会把不完整 JSON 当成 provider event，然后报“payload malformed”。真实语义却是 transport 在 terminal proof 前截断。

WHATWG 算法在 EOF 丢弃 pending data。渲染引擎随后依据“没有协议终态”产生：

```ts
{ kind: 'truncated', cause: 'eof', retryable: true }
```

这样协议错误与网络截断不会被混为一谈。

### TODO 1：让 decoder 跨 chunk 存活

在 async generator 外创建一次 TextDecoder。每次 decode 都传 `{ stream: true }`，循环结束后调用无参数 `decode()` flush。

`createLessonDecoder` 的第一个用例只喂入 BOM、一个中文和一个 emoji，而且每次只给一个 byte。它通过后再处理 line，不会被后面的 event state 噪音干扰。

### TODO 2：只 drain 完整行

实现：

```ts
function drainLessonLines(
  input: string,
  eof: boolean,
): {
  lines: string[]
  rest: string
}
```

扫描时维护 `start` 和 `index`，不要用会丢失 delimiter 语义的正则 split。其中一个 partition 专门切在每个 CR 之后，用来覆盖“chunk 以 CR 结束、下一块以 LF 开始”。

### TODO 3：按第一个冒号解析字段

不要 `line.split(':')`，data 中的 URL、JSON 都可能继续包含冒号。找到第一个冒号即可：

```ts
const colon = line.indexOf(':')
const field = colon === -1 ? line : line.slice(0, colon)
let value = colon === -1 ? '' : line.slice(colon + 1)
if (value.startsWith(' ')) value = value.slice(1)
```

把这段做成 `parseLessonField(line)`。它先用字面量用例证明 URL 里的冒号不会丢失；随后 event assembly 再把字段写进 EventState，unknown field 什么也不做。

### TODO 4：把 EOF 与空行分开

EOF 时可以处理此前由换行结束的完整 line，但绝不能凭空调用 `dispatch(state)`。独立用例只输入 `data: must-not-dispatch`，期望空数组；真实 fixture 尾部还留有 `data: discarded at eof`，两层证据共同防止“看似友好”的隐式 dispatch。

### TODO 5：枚举 partition，而不是只测一种 chunk

共享 contract 覆盖：

```ts
const partitions = [everyByte(bytes), splitAfterCr(bytes)]

for (const partition of partitions) {
  await expect(parse(partition)).resolves.toEqual(EXPECTED_EVENTS)
}
```

one-chunk 已在 event assembly checkpoint 中证明字段语义；这两种对抗 partition 必须得到与它完全相同的 `SseEvent[]`。

## 阅读 solution diff

最重要的变化不是某个 if，而是 parser 开始保存跨 chunk 状态：

```diff
- const text = new TextDecoder().decode(chunk)
- if (text.startsWith('data:')) events.push({ data: text.slice(5).trimStart() })
+ pending += decoder.push(chunk)
+ const drained = drainLessonLines(pending, false)
+ pending = drained.rest
+ for (const line of drained.lines) {
+   processLine(line, state, events)
+ }
```

循环结束后的 diff 同样关键：

```diff
+ pending += decoder.finish()
+ const drained = drainLessonLines(pending, true)
+ for (const line of drained.lines) processLine(line, state, events)
+ // 不 dispatch 剩余 state.data
```

## Invariant、成本与退化

### Invariant

任意 byte partition、任意合法 CR/LF/CRLF 组合，都不能改变 event 序列；provider adapter 看到的 JSON 字符串必须与 wire 中 dispatch 后的 data 完全一致。

### Trade-off

parser 保存 decoder、text rest 和 event state，代码比 split 多。TextDecoder 内部的未完整 code point 是有界的，但未换行的 field 和未 dispatch 的 data event 都可能随输入增长；因此正确性之外还必须配置 line、event 和 body size limit。

### 退化与失败

- 非法 UTF-8 默认被 TextDecoder 替换；如果产品要求硬失败，可启用 `{ fatal: true }`，但必须显式定义错误 outcome。
- 单条永不换行的超大 field 会让 text rest 持续增长，需要由 transport/body limit 保护。
- `retry` 是 EventSource 重连建议；你的 fetch proxy 是否自动重连，是 source 层的另一项产品决策。
- terminal marker 已在未派发的 EOF 残留中时，仍然不能“猜测完成”，结果是 truncated。

## 挑战题

1. 为 parser 增加 64 KiB 的单行上限。它应返回 failed，还是让 source 产生 truncated？说明分层理由。
2. 构造一个 `id:` 空值 fixture，证明后续 event 的 ID 被重置为空字符串。
3. 构造 `data:  x`，证明最终 data 保留一个前导空格。
4. 如果 proxy 把 gzip 解压后的数据重新任意分块，你的 parser 是否需要改动？为什么？

## 面试时怎么讲

> 我没有用双换行 split SSE，而是把 bytes → UTF-8 → lines → fields → provider JSON 分成独立状态机。TextDecoder 跨 chunk 保留多字节字符，line scanner 同时支持 CR/LF/CRLF，event buffer 处理多行 data、持久 id 与 retry。测试会枚举 every-byte partition，并证明 EOF residual 不 dispatch，从而把 transport truncated 与 provider malformed 分开。

下一课的 provider adapter 会消费这里产生的 message event；它不需要知道 byte 是怎样切开的。
