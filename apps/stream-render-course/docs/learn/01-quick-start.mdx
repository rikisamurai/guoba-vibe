# 先看见 Streaming Render 真正要解决的问题

AI Chat 的输出看起来只是“字符串不断变长”。但如果每收到一个 token 就让 React 解析并渲染一次全文，浏览器会反复计算用户根本看不到的中间状态。本章先不优化 parser；你会用一条可重复 trace，亲眼看见网络时钟与显示时钟为什么必须分开。

## 你会学到什么

完成本章后，你应该能不看代码回答四个问题：

1. `raw` 与 `visible` 为什么不能是同一个变量？
2. 为什么 7 个 delta 不一定对应 7 次 engine snapshot commit？
3. 为什么性能优化必须先有 M0 这个“慢但可信”的 oracle？
4. 为什么最终内容相同，仍然不能说明 streaming pipeline 相同？

我们只引入四个名词：

| 名词          | 它回答的问题                  | 本章中的证据               |
| ------------- | ----------------------------- | -------------------------- |
| raw           | 引擎已经接受了多少真实文本？  | 所有 delta 的有序拼接      |
| visible       | 此刻允许 React 展示多少文本？ | 每次 snapshot 中的可见前缀 |
| arrival clock | 数据什么时候到达？            | trace 中每条记录的 `at`    |
| display clock | 引擎什么时候发布新版本？      | commit 时间与 revision     |

> **先记住一个边界：** raw 是事实，visible 是产品决策。任何平滑动画、预览修补或帧批处理都只能改变 visible，不能改写 raw。

## 先观察失败：最终正确，不等于过程健康

假设 provider 在 14 ms 内连续送来 7 个片段：

```text
0ms   "## 报告\n\n"
2ms   "**结"
4ms   "论**："
6ms   "流式"
8ms   "渲染"
10ms  "需要"
14ms  "两只时钟。"
```

60 Hz 屏幕大约每 16.7 ms 才有一次显示机会。M0 却在第一帧出现前完成了 7 次“拼接 → 全文 Markdown parse → Render IR → React snapshot”。用户最终只看到第 7 个状态，前 6 次工作没有产生可观察价值。

### M0 做了什么

```ts
for await (const delta of source) {
  raw += delta
  const document = parseMarkdown(raw)
  publish({ raw, visible: raw, document })
}
```

它的优点不是快，而是**语义简单**：任意 prefix 都由完整 parser 从头计算。因此后续 M1–M4 的每次优化，都可以拿同一 prefix 的结果与 M0 对照。

### M4 多做了哪些决定

```text
provider delta ──→ raw buffer ──→ arrival metrics
                         │
                         └── display scheduler ──→ visible snapshot ──→ React
```

M4 会立即接受 raw，却把“什么时候公开新 visible”交给 scheduler；随后增加 suffix reparse、稳定 block identity 与重型节点 revision guard。同一帧内到达的多个 delta 可以合并；终态到达后仍要 drain，确保已接受的 raw 全部可见。产品使用的 `production` 预设建立在这条能力链上，但本章直接选择 M4，避免把预设名当成新算法。

## 逐层看同一条 trace

把一次运行拆成五层，你就不会把“网络快”误认为“渲染快”：

```text
Timed trace
  ↓  at=0,2,4...（arrival clock）
ReplaySource / provider source
  ↓  typed delta
Engine accepts raw
  ↓  raw length 10, 13, 17...
Scheduler publishes visible
  ↓  revision 1, 2...
React renders Render IR
```

### 1. Source 只负责按时交付

Source 不知道 React，也不决定 commit。确定性 replay 与真实 provider 的共同边界都是 `AsyncIterable<SourceEvent>`。

### 2. Engine 先接受，再显示

收到 delta 时先更新 raw 与 `throughInternalSeq`。这一步不能等待下一帧，否则取消、协议终态和诊断看到的事实会落后于网络。

### 3. Scheduler 只控制公开频率

Scheduler 维护 pending frame。已经安排一帧后，新 delta 只把 dirty buffer 变长，不能继续安排第二个同帧任务。

### 4. Parser 处理 visible prefix

本章暂不实现局部 parse。M0 与 M4 的最终 canonical parse 必须相等；preview 工作量可以不同。

### 5. React 只订阅 snapshot

React 不应直接订阅 provider token。它订阅的是引擎已经决定公开的 `RenderSnapshot.revision`。本章的 `metrics.commits` 统计 engine snapshot commit；真正的 React commit 与 `actualDuration` 要到 Profiler 页面单独测量，二者不能混叫。

### TODO 1：用真正的 M4 run 替换占位别名

两个 run 必须共享 VirtualClock，但各自拥有 source iterator：

```ts
const m4 = engine.start({
  source: new ReplaySource(clock, records),
  profile: 'M4',
  reveal: 'direct',
  trace: 'full',
})
```

共享 Clock 让时间可比；独立 iterator 防止一条 run 把另一条的数据消费掉。删掉 starter 中的 `const m4 = m0`，用上面的 run 替换它。

### 已提供：推进时间，而不是等待真实时间

测试里不要 `setTimeout(20)`。starter 与 solution 都调用同一个共享 helper：

```ts
const [m0Result, m4Result] = await settleRuns(clock, [m0, m4])
```

如果 Clock 暂时没有 task，harness 会先让 source 的 microtask 注册完成；如果终态还在 draining，它再排空明确的 VirtualClock task，而不是随机 sleep。

### contract 怎样判定你完成了

先比较语义：

```ts
const m0Part = m0Result.snapshot.parts.find((part) => part.kind === 'answer')
const m4Part = m4Result.snapshot.parts.find((part) => part.kind === 'answer')
expect(m4Part?.raw).toBe(m0Part?.raw)
expect(m4Part?.document).toEqual(m0Part?.document)
```

再比较工作：

```ts
expect(m4Result.snapshot.metrics.commits).toBeLessThan(m0Result.snapshot.metrics.commits)
```

不要反过来。候选实现如果文本错了，commit 再少也没有意义。

## 复盘：哪些东西必须永远成立

### Invariant

```text
normalize(M0.final(raw)) === normalize(M4.final(raw))
```

并且所有 accepted delta 的有序拼接必须等于 settled raw。preview repair、动画字符和临时光标都不能进入 raw。

### Trade-off

减少 commit 会增加 raw → visible 延迟。60 Hz 下等待一帧通常约 0–16.7 ms；这不是免费优化，而是把不可见的重复工作换成有上限的显示等待。

### 退化条件

- 标签页进入后台时，`requestAnimationFrame` 可能暂停。
- 一个超长 Markdown root block 没有稳定 checkpoint 时，M4 的 parse 工作可能退化为全文重算。
- terminal 在 frame 前到达时，不能直接 settled，必须先 drain 已接受 raw。

## 面试时怎么讲

不要只说“我用 rAF 节流 token”。更完整的表达是：

> 我把 provider arrival 与 UI display 建模为两只时钟。引擎立即接受 raw，显示层按 frame 发布 visible；用 M0 作为语义 oracle，并让 M4 在同一 trace 下证明终态等价、snapshot commit 更少。VirtualClock 负责验证排序和 drain，React Profiler 再单独测真实 commit 与 actualDuration。
