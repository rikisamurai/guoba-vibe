# raw 是原文，visible 是对当前 raw 的完整解析结果

```ts
interface Snapshot {
  raw: string
  visible: string
  parseCount: number
}
```

## 两个字段分别回答什么

| 字段       | 问题                           | 谁能改变它  |
| ---------- | ------------------------------ | ----------- |
| raw        | 引擎已经接受了哪些真实 delta？ | ingest      |
| visible    | 完整解析当前 raw 后展示什么？  | M0 parser   |
| parseCount | 到目前为止完整解析了几次？     | M0 renderer |

输入 `**流式` 时标记未闭合，tiny parser 暂时原样显示；补上 `渲染**` 后，visible 变为 `<strong>流式渲染</strong>`。两个字段从此不应混为一个 string。

exercise 先算出新 `raw`，却错误地解析旧 `snapshot.raw`。结果 visible 永远落后一个 delta——典型的 stale state bug。

## 最小 M0 数据流

```text
delta arrives
  → raw = raw + delta
  → visible = fullParse(raw)
  → parseCount = parseCount + 1
  → publish immutable snapshot
```

M0 刻意在每个 delta 后发布。它以后可能很慢，但逻辑最容易验证，所以会成为其他策略的 oracle。

Profiler 会把每次完整解析的输入长度累加为 `previewParsedCodeUnits`。本课只记录 `parseCount`，先理解“每段都全量解析”，后面再量化总工作量。

## Checkpoint：你能读懂 timeline 吗

- [ ] 第一次 push 后 `parseCount === 1`。
- [ ] 未闭合 `**` 暂时原样显示，raw 一字不改。
- [ ] 第二次 push 解析完整 raw，visible 变成 `<strong>`。

**Invariant：** 每次 push 后 `raw = orderedConcat(deltas)`，`visible = fullParse(raw)`；raw 永远不含 parser 产物。

**Trade-off：** 每个 delta 都发布，正确性直观，parse/React 工作可能随 delta 数快速增长。

**退化条件：** provider 一次返回完整 reply 时，M0 自然退化成 01 的单次提交。

## 常见错误

| 症状                     | 根因                          |
| ------------------------ | ----------------------------- |
| raw 对、visible 落后一段 | 解析了旧 snapshot             |
| raw 里出现 `<strong>`    | 把渲染结果写回原文            |
| parseCount 少一次        | 某个 delta 没经过 M0 baseline |

## 面试时怎么讲

> 我把 raw 视为不可改写的 provider truth，把 visible 视为显示策略。即使最简单模式里两者总相等，也分别建模；这样后续做批处理或平滑显示时，不会为了 UI 效果污染原始内容。
