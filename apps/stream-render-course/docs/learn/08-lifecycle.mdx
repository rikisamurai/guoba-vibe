# 连接结束了，回答就一定成功了吗？

**修改文件：** `apps/stream-render-lab/src/my-chat/read-answer.ts`。先通过 A 段；本课把解析结果接回请求生命周期。

## 第一步：复现一次误报成功

打开 <LabLink path="/project?source=mine">我的 Mini Chat</LabLink>，选择中途断开并发送。记下已收到的文本与状态，再切换参考实现执行同一场景。

```bash
pnpm --filter stream-render-lab practice test lifecycle
```

初始实现尚未正确覆盖 EOF。预期发现：响应体读完不代表协议证实回答完成。先保留这个失败，不要修改 UI 文案来掩盖错误状态。

## 第二步：把两个“结束”分开

从 `read-answer.ts` 进入共享 `consume-response.ts` 的 done 分支，再检查 `read-event.ts` 提供的终态信息：

- 正常完成：有协议结束证据，且没有不完整或错误原因。
- 截断：流到了 EOF，却缺少必需的协议结束证据。
- 不完整：服务商明确说明长度限制等原因。
- 取消：本轮的 signal 被主动终止。
- 失败：HTTP、读取或协议错误。

`consumeResponse` 返回协议结果或未证实终态的空值。在自己的 `read-answer.ts` 中修正这个空值的回退判断。保留此前接受的正文；不能因为结尾有问题就把前面正确的字清空。

## 第三步：沿着停止按钮追踪 signal

阅读 `src/learn-project/use-mini-chat.ts`：每轮一个 AbortController，signal 从 fetch 传到读取层。停止调用 abort，读取层释放 reader 的锁，并停止继续发布正文。

沿自己的 `read-answer.ts` 进入共享 `consume-response.ts`，检查 signal、循环退出与 finally 路径。**取消是协作行为**，不是撤回已执行回调；把 loading 改为 false 不足以取消请求。

项目外层还用递增的请求编号拒绝旧回调。定位 `current()` 的判断，确认一轮结果只能修改自己的回答。

## 第四步：验证尾部和下一轮

1. 分段发送，出现文字后停止：已有文字保留，状态不再变回接收中。
2. 立即重新发送：新的回答独立增长，旧轮不会继续追加。
3. HTTP 错误后重试：新增一次尝试，原错误记录仍在。
4. 完整发送：尾段不丢，正常完成。

按帧发布会引入待显示文本。结束前需交出已接受的尾部，再清掉待执行帧；C1 会让你在 `publish.ts` 实现这件事。

## 第五步：验收自己的读取链

```bash
pnpm --filter stream-render-lab practice test lifecycle
pnpm --filter stream-render-lab practice test lifecycle --reference
```

预期：EOF、取消、HTTP 错误与协议完成被区分；取消后不再接受新正文。浏览器步骤另行验证状态、历史和迟到更新，单元验收不能代替 UI 观察。

重试是新请求。没有服务端事件 ID 与重放协议时，不能把结果直接接到旧半截后面并称为断点续传。
