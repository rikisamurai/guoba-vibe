# 解析出事件以后，哪些内容可以显示？

**修改文件：** `apps/stream-render-lab/src/my-chat/read-event.ts`。本课只处理完整 SSE 事件，字节与行状态继续由 A2、A3 的代码负责。

## 第一步：找出没有正文的事件

在 <LabLink path="/playground?demo=network-inspector&source=mine">网络观察器</LabLink> 对照完整事件与提取正文。开始事件可能只有 role，结束事件可能只有 finish_reason；它们不会都产生文本增量。

```bash
pnpm --filter stream-render-lab practice test provider
```

初始实现可以提取常见正文，但结束原因等边界尚未完整。先记下失败输入，不要把没有 content 的事件一律当成错误。

## 第二步：按协议读取字段

本课固定端点使用 Chat Completions 风格事件：

```json
{ "choices": [{ "index": 0, "delta": { "content": "你好" }, "finish_reason": null }] }
```

在 `read-event.ts` 中分别处理正文与结束信息。只把 `delta.content` 中有效的文本交给正文；不要把 role、reasoning 或整个 JSON 字符串追加进回答。

`[DONE]` 是该协议使用的标记，不是 JSON。先识别标记，再解析 JSON，并沿用项目已经定义的事件结果类型。

## 第三步：修复错误的完成判断

在源码中找到 finish_reason 的分支，区分正常结束与因长度等原因没有完整回答。保留原因交给读取层，不能让后面的 `[DONE]` 把已经记录的不完整结果覆盖成成功。

按验收失败逐项修复。不要复制参考实现后只看绿灯；说明是哪一个输入让原来的判断不成立。

## 第四步：核对正文和终态

```bash
pnpm --filter stream-render-lab practice test provider
pnpm --filter stream-render-lab practice test provider --reference
```

预期：正文只累积文本增量，结束原因正确保留；角色事件与空 delta 不增加正文。完整读取流程将在 B1 验证 EOF、取消与协议终态。

回到 <LabLink path="/project?source=mine">我的 Mini Chat</LabLink>，普通回答应保持不变。修复边界不能破坏已经可用的路径。

## 第五步：别把 delta 当成 token

| 计数            | 能从哪里知道                                       |
| --------------- | -------------------------------------------------- |
| 读取次数        | reader.read 的实际结果                             |
| 事件数量        | SSE 解析器实际派发                                 |
| 正文长度        | 已接受的字符串，但 JS length 也不是 Unicode 字符数 |
| 模型 token 数量 | 服务商用量或对应 tokenizer，不能由以上数量直接推算 |

一次事件可以带多个 token 的文本，或完全不带正文。网络“流式”描述交付方式，不保证它一 token 一 token 到达。

**验收：** 能沿着 bytes → text → event → delta 指出自己的四个模块；换切分方式后正文与终态不变。
