本课第一次把通用 SSE event 变成领域事件：

```ts
type ChatEvent =
  | { kind: 'reasoning-delta'; text: string }
  | { kind: 'content-delta'; text: string }
  | { kind: 'finish'; reason: string }
  | { kind: 'done' }
```

## 先看一条真实 wire 的三种语义

```text
data: {"choices":[{"index":0,"delta":{"reasoning_content":"先分析"}}]}

data: {"choices":[{"index":0,"delta":{"content":"答案"},"finish_reason":"stop"}]}

data: [DONE]

```

- SSE parser 只看到三条 `data`。
- adapter 把前两条 JSON 映射为 delta，并记录 `finish_reason`。
- `[DONE]` 是 transport stream 中的 terminal proof，不应当送进 `JSON.parse`。

本课 fixture 只请求 choice 0，因此 workshop event 暂不携带 index；生产 adapter 必须把 `choiceIndex` 当结构地址，而不是全局 sequence number。Chat Completions payload 没有可用来检测倒序的协议序号。

## Checkpoint：四层边界没有混在一起

- [ ] SSE parser 不调用 `JSON.parse`。
- [ ] adapter 不关心 byte/text chunk 如何切分。
- [ ] reasoning 与 content 分通道。
- [ ] `[DONE]` 不当 JSON，EOF 也不冒充 `[DONE]`。

**Invariant：** mini-chat 的 raw content 只由有序 `content-delta.text` 拼接；provider JSON 外壳永不进入 raw。

**Trade-off：** 每种 provider interface 都需要 adapter，但引擎和 React 获得稳定、typed 的事件模型。本课单 choice 类型更小，多 choice 时必须扩展 origin。

**退化条件：** 多 choice 请求会产生多条并行地址；若产品只显示 choice 0，过滤必须是显式产品规则，而不是排序规则。

## 常见错误

| 错误                        | 后果                             |
| --------------------------- | -------------------------------- |
| `[DONE]` 进入 `JSON.parse`  | 正常终态被报告为 malformed JSON  |
| 用 `choiceIndex` 检测倒序   | 把结构地址误当序列号             |
| 丢弃空 delta event          | 可能漏掉 role 或 finish metadata |
| reasoning append 到 content | UI 与复制结果混入思考文本        |

如果 transport 在 `[DONE]` 前 EOF，生命周期层应给出 `truncated`，不能由 adapter 静默补成 done。
