## 为什么暂时不接网络

只要最终 transcript 都不可靠，加入 chunk 只会增加噪声。先固定三条最小语义：

```ts
type Message = {
  role: 'user' | 'assistant'
  text: string
}
```

1. user 消息先出现；
2. 完整 reply 对应一条 assistant 消息；
3. assistant 内容与输入 reply 逐字相同。

本课用同步 fixture 压缩变量；接真实请求时，输入 seam 会换成返回 `Promise<string>` 的 complete 函数，transcript invariant 不变。

打开 exercise，你会看到 fixture 已经有完整 reply，但 `messages` 只返回 user。这模拟了常见错误：请求成功，不代表结果已经进入 UI state。

## 最小原理：把 transcript 当作值

不要让这个练习掺入 React state 或全局 store。先实现一个纯函数：同样的 fixture，得到同样的消息数组。

```ts
export function createStaticChat(input: Fixture): StaticChat {
  // TODO 01：在 user 后追加 assistant reply
  return { messages: [{ role: 'user', text: input.prompt }] }
}
```

## Checkpoint：最终真相成立了吗

- [ ] transcript 恰好两条消息，顺序为 user → assistant。
- [ ] reply 中的中文、换行和标点没有被处理。
- [ ] fixture 相同，多次运行结果相同。

**Invariant：** assistant `text` 必须逐字等于 fixture 的完整 reply。

**Trade-off：** 用户必须等待完整回复，没有渐进反馈；但状态模型最简单，适合作为最终内容 oracle。

**退化条件：** 回复越长，首屏等待越久；正确性不受影响，体验会变差。

## 常见错误

| 错误                     | 为什么不对                  |
| ------------------------ | --------------------------- |
| assistant 放在 user 前面 | transcript 的因果顺序被反转 |
| `reply.trim()`           | 悄悄改写 provider 真相      |
| catch 后返回空数组       | 把失败伪装成“没有回答”      |

## 挑战题

给 fixture 的 reply 加上首尾换行。你的 transcript 是否仍逐字保留？为什么这里不应该替用户 `trim()`？

## 面试时怎么讲

> 我不会一上来写复杂的 streaming state。先用纯函数建立非流式最终结果，把它作为后续每个增量前缀和终态的 correctness oracle；这样性能优化不会悄悄改变内容语义。
