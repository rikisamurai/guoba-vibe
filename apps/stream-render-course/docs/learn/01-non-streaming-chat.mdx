# Streaming 之前，先完成一次正确的非流式对话

这一课还不处理 chunk。你会实现一次最小但真实的**异步 chat turn**（一条用户消息及其对应的一次 assistant 回答）：用户提交 prompt，程序等待一个 `Promise<string>`，拿到完整 reply 后再更新对话。

## 这一课要建立什么基线

DeepSeek Chat Completions 在非流式模式下会返回一条完整 assistant message；其 API 中 `stream` 默认为 `false`。具体响应结构可查看 [DeepSeek Create Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion)。

我们暂时用可控的 `complete(prompt): Promise<string>` 代替真实 HTTP 请求，但保留请求最重要的异步边界：调用后不能立刻得到回答，必须等待 Promise 完成。

一次对话只经过三个 UI 状态：

```text
idle      用户还没有发送
  ↓ send
waiting   用户消息已经显示，正在等待完整回答
  ↓ await complete(prompt)
completed 用户消息后追加一条完整 assistant 消息
```

`idle / waiting / completed` 是本课定义的 **UI 状态**，不是 DeepSeek 协议中的事件名称。

## 读懂三个输入

打开 `exercise/index.tsx`，函数签名如下：

```ts
sendNonStreamingTurn({ prompt, complete, publish }): Promise<void>
```

`ChatSnapshot` 是本项目对“某一时刻完整对话状态”的命名。三个参数分别代表：

| 参数       | 含义                                                                                                        |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| `prompt`   | 用户刚刚发送的原始文本。                                                                                    |
| `complete` | 模拟非流式 AI 请求的异步函数。传入 prompt，最终返回完整 reply。                                             |
| `publish`  | 本项目传入的状态回调：每调用一次，就把一个新的 `ChatSnapshot`（对话状态快照）交给界面。它不是网络协议术语。 |

函数返回 `Promise<void>`，表示调用者可以等待这次 chat turn 完成；真正的对话结果通过 `publish` 交给界面。

当前 starter 已经做对了前半段：

```ts
const userMessage = { role: 'user' as const, text: prompt }
publish({ phase: 'waiting', messages: [userMessage] })

await complete(prompt)
// TODO 01: publish the completed snapshot with the unchanged reply.
```

测试失败的原因不是“请求没有返回”，而是 `await` 的结果被丢掉了：程序只发布过 `waiting`，从未发布 `completed`。

## 先预测，再写代码

假设 `complete(prompt)` 还没有完成，此时唯一合法的 snapshot 是：

```ts
{
  phase: 'waiting',
  messages: [{ role: 'user', text: prompt }],
}
```

assistant 消息不能提前出现，因为你还没有 reply。等 Promise 完成后，第二个 snapshot 才能是：

```ts
{
  phase: 'completed',
  messages: [
    { role: 'user', text: prompt },
    { role: 'assistant', text: reply },
  ],
}
```

注意第二次不是只发布 assistant。一个 snapshot 描述的是**当前完整对话状态**，所以原来的 user 消息仍然存在。

## 实现唯一 TODO

把 `await complete(prompt)` 的返回值保存为 `reply`，然后发布完成状态：

```ts
const reply = await complete(prompt)

publish({
  phase: 'completed',
  messages: [userMessage, { role: 'assistant', text: reply }],
})
```

这里不要 `trim()`、拆分或重新拼接 `reply`。非流式 API 已经给出了完整正文，本课的职责只是把它原样放进 assistant message。

## Contract 如何检查“等待”真的发生过

测试没有让 `complete` 立即返回。它先创建一个暂未完成的 Promise，然后调用你的函数：

```ts
const settled = sendNonStreamingTurn({ prompt, complete, publish })

expect(published).toEqual([waitingSnapshot])

completion.resolve(reply)
await settled

expect(published).toEqual([waitingSnapshot, completedSnapshot])
```

这证明了两件不同的事：

1. `complete` 完成前，user 已经出现，phase 是 `waiting`；
2. `complete` 完成后，恰好再发布一次，phase 是 `completed`。

如果测试只等待函数结束再看最终数组，它就无法发现“等待期间界面还是空白”这种体验问题。

## Solution diff

```diff
-await complete(prompt)
-// TODO 01: publish the completed snapshot with the unchanged reply.
+const reply = await complete(prompt)
+
+publish({
+  phase: 'completed',

+})
```

## 本章 Checkpoint

- [ ] 我能解释为什么 `complete` 返回 Promise，而不是直接返回 string。
- [ ] Promise 完成前，snapshot 中已经有 user 消息和 `waiting` 状态。
- [ ] Promise 完成后，只追加一条完整 assistant 消息。
- [ ] assistant 文本逐字等于 `complete` 返回的 reply。

**Invariant：** 完成状态中的消息顺序始终是 user → assistant，assistant `text` 与完整 reply 完全相同。

**Trade-off：** 状态和实现都很简单，但用户必须等完整 reply 返回后才能看到答案。

**退化条件：** 模型生成时间越长，`waiting` 保持越久；内容正确性不变，等待体验会变差。

## 常见错误

| 错误                                    | 会发生什么                             |
| --------------------------------------- | -------------------------------------- |
| `await complete(prompt)` 但不保存返回值 | 请求完成了，assistant 仍不会进入状态。 |
| 等 reply 返回后才第一次 `publish`       | 等待期间用户自己的消息也看不见。       |
| 第二次只发布 assistant message          | user 消息从完整 snapshot 中消失。      |
| 对 reply 调用 `trim()`                  | 悄悄改变 Provider 返回的内容。         |
| 调用两次 `complete(prompt)`             | 同一个 turn 被重复请求。               |
