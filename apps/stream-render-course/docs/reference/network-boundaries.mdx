## 先说人话：同一个“流式”里有三种节奏

假设浏览器先后读到下面两个 chunks：

```text
第 1 次读取：data: {"choices":[{"delta":{"content":"Hel
第 2 次读取：lo"}}]}\n\n
```

第二次读取结束后，SSE 解析器才拿到空行，因而可以派发一条完整事件；DeepSeek 协议适配器再从 JSON 的 `choices[].delta.content` 中取出文本 `Hello`。渲染层还可以把它与紧随其后的文本增量合并，在下一次状态更新里一起显示。

所以这里可能发生：

```text
2 个 chunks
→ 1 个 SSE event
→ 1 个 DeepSeek choices[].delta.content："Hello"
→ 可以先不更新，稍后与其他文本增量合并为 1 次显示文本状态更新
```

箭头两侧不是一一对应关系。读取边界可能切在 JSON 中间；一次读取也可能包含多条完整 SSE events；多个文本增量又可能合并为一次显示文本状态更新。

## 这些词分别来自哪里

| 词语                          | 来源                                                                                                                             | 在本课程中的准确含义                                                                                                                                   |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **chunk**                     | [WHATWG Streams 标准](https://streams.spec.whatwg.org/#model)                                                                    | 从 `ReadableStream` 一次读到的一段数据。HTTP 响应体中通常是 `Uint8Array`；边界是任意的，不对应一个 TCP segment（TCP 报文段），也不保证是一条完整消息。 |
| **SSE event**                 | [WHATWG HTML 的 Server-Sent Events 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream) | `text/event-stream` 按行解析后派发的一条事件。多个 `data:` 行可以组成同一事件，空行通常表示事件结束。                                                  |
| **`choices[].delta.content`** | [DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion)                                        | DeepSeek 流式事件中的文本增量字段。它是服务商接口字段，不是 Web 协议的统一名称。                                                                       |
| **raw**                       | 本项目概念                                                                                                                       | 渲染引擎已经接受并按顺序拼接的模型正文。它记录内容事实，不因为显示较慢而丢字。                                                                         |
| **visible**                   | 本项目概念                                                                                                                       | 当前准备交给界面显示的正文版本。它可以暂时落后于 `raw`，但响应结束时必须追平。                                                                         |
| **显示文本状态更新**          | 本项目概念                                                                                                                       | 引擎把一个新的 `visible` 版本交给界面状态。它不等于 React 已提交 DOM 更新，也不等于浏览器已把像素绘制出来。                                            |

## 三步观察实验

下面的实验使用同一份可重复输入，同时运行**逐增量更新（M0）**和**合并更新（M4）**。括号中的 M0、M4 只是本项目的策略编号，不是行业标准：前者更频繁地更新显示文本，后者会合并一部分更新；两者最后必须显示同一份回答。

### 观察一：读到 chunk，不代表正文立刻增加

1. 点击“读取下一个 chunk”。
2. 看 chunk 计数和读取时间线是否已经出现记录。
3. 再看已接收文本（项目字段 `raw`）：在完整 SSE event 形成前，它可能仍然没有增长。

这是正常现象。一条 SSE event 可以被拆到多个 chunks 中；在事件结束标记到达前，SSE 解析器不能把半截 JSON 当作模型内容。

**检查点：** 此时网络没有“卡住”，只是应用还没有得到一条可以安全解释的完整协议事件。

### 观察二：已接收文本可以领先当前显示文本

继续点击“读取下一个 chunk”，直到完整 SSE event 带来一个 DeepSeek `choices[].delta.content`。此时已接收文本（`raw`）先增长；如果界面状态还没有更新，当前显示文本（`visible`）会暂时落后。

点击“显示已接收文本”后，再看 `visible` 是否追上。这个短暂差值表示**已经收到但尚未显示**的正文，不代表内容丢失。

**检查点：** 如果 `raw` 是 104 个字符、`visible` 是 82 个字符，那么待显示的是 22 个字符，而不是又缺少了一条网络消息。

### 观察三：先核对内容，再比较状态更新次数

点击“继续到完整回复”，然后按顺序检查：

1. 逐增量更新（M0）和合并更新（M4）的最终已接收文本是否完全相同；
2. 两种策略的最终显示文本是否都追平已接收文本；
3. 在前两项成立后，合并更新（M4）的显示文本状态更新次数是否更少。

前两项证明内容正确，第三项才是性能线索。如果只看“更新更少”，一个丢掉半句话的实现也可能看起来更快。

**检查点：** 本实验只能证明合并更新策略以更少的显示文本状态更新到达相同终点。它不等于 React commit（React 把变更提交到 DOM）的次数更少，也不等于 browser paint（浏览器绘制像素）一定更快；后面的性能分析页会分别测量这些阶段。

## 你刚刚看见的完整边界

```text
ReadableStream 中的 chunk
→ UTF-8 文本
→ SSE event
→ DeepSeek choices[].delta.content
→ 已接收文本（raw）
→ 当前显示文本（visible）
→ 显示文本状态更新
→ React 提交 DOM 与浏览器绘制画面
```

这一课只要求你能指出每条边界“输入是什么、输出是什么”。后续课程会从左到右逐层实现，而不是把所有带文本的东西塞进一个流式函数。

## 自测：下面哪句话正确

- [ ] 一次 `reader.read()` 一定对应一个 TCP segment（TCP 报文段）。
- [ ] 一条 SSE event 一定只包含一个字符。
- [x] 多个 DeepSeek `choices[].delta.content` 可以合并为一次显示文本状态更新。
- [ ] `raw` 暂时大于 `visible` 就表示丢字。

答案是第三项。chunk 的边界不表达协议语义；`choices[].delta.content` 的大小由 DeepSeek 决定；显示文本何时更新又属于渲染调度。

## 本章没有证明什么

- 没有观察真实 TCP segment（TCP 报文段）；Lab 记录的是应用从 `ReadableStream` 读到的 chunk。
- 没有证明一次显示文本状态更新等于一次 React commit 或一次 browser paint。
- 没有证明合并更新（M4）在所有输入上都更快；这里只建立后续课程要验证的问题。

## 面试时怎么讲

> 我会区分 ReadableStream 的 chunk、SSE event、DeepSeek 文本增量和显示文本状态更新。它们分别属于流读取、协议、服务商接口和渲染调度，边界并不一一对应。先把这些层分开，才能定位乱码、半截事件、丢内容和高频渲染分别发生在哪里。
